FIXES APPLIED — FIXED 25b (root cause found and fixed)

6. ROOT CAUSE of the missing cumulative table identified: it was step 6 of
   RUN_REPORT_GENERATOR.bat (scripts/to_pdf.ps1), NOT generate_report.js.
   generate_report.js writes and byte/structure-verifies out\report.docx
   correctly (this was confirmed - the table image is present and wired in
   at that point). Step 6 then opens THAT SAME FILE in real Microsoft Word
   via COM to export a PDF, calls Fields.Update() / TablesOfContents
   .Update() / Repaginate() (all of which mark the doc as modified in
   Word's memory), and then called Document.Close() with no explicit
   "don't save" argument. Word's unattended automation can silently
   resave the source .docx as a side effect of that close - and whatever
   Word's own renderer did with the picture drawing while repaginating
   ended up dropping it, leaving an empty (but correctly formatted)
   paragraph where the table was. This happened AFTER generate_report.js
   had already produced a correct, verified file - so no check inside
   generate_report.js could ever have caught it.

   Fixed in two places:
   - scripts/to_pdf.ps1: now opens a throwaway TEMP COPY of the docx for
     Word to convert (never the original out\report.docx), opens it
     read-only, sets DisplayAlerts=wdAlertsNone, and closes it with an
     explicit wdDoNotSaveChanges (0). Nothing in this script can write to
     out\report.docx anymore, even in principle.
   - RUN_REPORT_GENERATOR.bat: hashes out\report.docx before and after
     the PDF step and hard-fails with a clear error if it changed at all,
     so this class of bug can never again reach a submitted report
     silently - even if some future edit to the PDF step reintroduces it.

FIXES APPLIED — FIXED 26 (actual root cause found and fixed)

8. ACTUAL ROOT CAUSE of the picture going blank in real Word (found after
   FIXED_25c still reproduced it): every embedded picture the `docx` npm
   library writes gets the same hardcoded <wp:docPr id="1"> and
   <pic:cNvPr id="0"> - see https://github.com/dolanmiu/docx/issues/2719.
   All 24 pictures in this report (cumulative table + every unit's KPI /
   savings / kaizen / owner images) had id="1". This is invalid per the
   OOXML spec (ids must be unique within a document part), and Word
   tolerates it inconsistently: depending on version/patch it can render
   only one of the duplicate-id pictures and leave every other one as a
   blank, correctly-formatted paragraph - no red-X, no error, nothing a
   byte-level or XML-structure check would ever catch, because the XML
   and the image data are both completely valid on their own. This is
   why every previous check in this tool (media byte-verification,
   <w:drawing> placement counting) passed while the picture still didn't
   render for the actual user.

   Fixed: patchGoldenLayout() now also renumbers every <wp:docPr id="...">
   and <pic:cNvPr id="..."> in word/document.xml and both header/footer
   parts to be sequential and unique, immediately after packing and
   before the byte/structure verification step. This removes the
   ambiguity Word was resolving inconsistently, rather than trying to
   guess which duplicate Word's renderer would keep.

FIXES APPLIED — FIXED 27 (fixes the bug that FIXED 26 introduced)

9. FIXED_26's own renumbering was still broken: patchUniqueDrawingIds()
   reset its docPr/cNvPr counters to 0 SEPARATELY for each part
   (document.xml, then header1.xml, then header2.xml, then footer1.xml,
   then footer2.xml). That makes ids unique WITHIN each file, but
   header/footer parts render on the SAME physical page as the body
   content, so document.xml ending up with id="1" while header1.xml
   (present on every content page) also has its own id="1" reproduces
   the exact same "two shapes, same id, same page" ambiguity this
   function was written to eliminate - just moved from body-vs-body to
   body-vs-header/footer. Verified directly against a delivered
   report.docx: id="1" and id="2" collided between document.xml and
   header1.xml, id="1"/"2"/"3" collided between document.xml and
   header2.xml, and id="1" collided between document.xml and each of
   footer1.xml/footer2.xml.

   Fixed: docPrCounter and picCounter are now declared ONCE, outside the
   per-part loop, so numbering continues across document.xml -> header1
   -> header2 -> footer1 -> footer2 without ever resetting. Every picture
   id in the packaged .docx is now globally unique, not just unique per
   file.

   Also added verifyGlobalUniqueDrawingIds(), run inside the same
   attempt/retry loop as the existing media-byte and drawing-placement
   checks in packAndVerify(): it re-scans the packed document.xml +
   both headers + both footers together and fails the attempt (rebuild
   and retry, same as a missing asset) if any docPr or cNvPr id repeats
   across parts. This turns a silent, Word-version-dependent rendering
   coin flip into a build-time failure that's caught before a file is
   ever written.

FIX (header-to-content gap still not matching GOE-164 after the previous
spacing pass - root cause was different from what it looked like):

The previous fix increased `spacing.before` on section headings (Heading1/2/3,
Acknowledgement, Index) to match GOE-164's actual style values. That worked
correctly for the COVER PAGE title (which is the literal first paragraph of
the document), but had ZERO visible effect on the Acknowledgement page, the
Index page, "1. Introduction of GOE", every "2.x UNIT NAME" page, and the

FIX (blank pages appearing after the cumulative-outcome table and elsewhere -
the actual cause of "cumulative on next page", "KPI table on next page", and
"way too much space between header and content"):

The previous fix's pageBreak() helper inserted TWO separate paragraphs: an
empty one containing only the manual page-break run, followed by a second
tiny spacer paragraph. This had a real, reproducible bug: if the content
immediately before the break already filled the current page almost exactly
to its bottom edge (which the GOE-level cumulative-outcome table does, right
up against the "1.3 GOE-level Outcomes" page), that near-empty break-carrier
paragraph's own line box - which uses the document's default 11pt style,
larger than it looks - could itself fail to fit in the sliver of space left
on the page. It would then spill onto a page of its own: a genuinely blank
page containing nothing but that invisible paragraph, with the real content
(page break, then heading) pushed one whole page later than intended. This
was confirmed directly: reproducing the same cumulative-outcome table at its
real size produced an identical blank page, which disappeared once the fix
below was applied.

Fixed by collapsing pageBreak() to a single paragraph: the same tiny 7pt
near-invisible spacer, but marked with `pageBreakBefore: true` on itself
rather than being preceded by a separate break-only paragraph. A paragraph
property cannot independently overflow onto its own page the way a whole
separate flow paragraph can, since there is no second paragraph left that
could fail to fit - there is only the one spacer paragraph, and it is the
thing that starts the new page.

Verified by reproducing the exact real cumulative-outcome table (extracted
from the previously-broken report) at its real 1732x1011 size: "2. Unit-Wise
Summary" now lands on the very next page as intended, with no blank page in
between, and a full-document visual sweep across all pages found no other
blank-page or content-ordering anomalies.

FIX (previous fix over-corrected: cumulative table now relocating entirely,
leaving large blank gaps on two pages - "table going to next page", "extra
space near the 2. Unit-Wise Summary heading"):

The prior fix bound the cumulative-outcome image to its caption with
keepNext:true so they couldn't be split apart. That solved the orphaned-
caption bug, but introduced a new problem: "1.1 Basic Information" and
"1.2 GOE Overview" above the table vary a lot in length (the USP bullet
alone can run 5-6 lines depending on how many product/process fields are
filled in), so how much room is left on that page for the table is
unpredictable. When a longer-than-usual USP paragraph left too little room,
keepNext correctly refused to split the image from its caption - but since
neither piece fit in what was left, it moved the ENTIRE ~4-inch image+caption
pair to the next page as a unit, leaving most of the first page blank below
"1.2 GOE Overview" and most of the second page blank below the relocated
table. This is worse than the original bug, not better.

Fixed by giving "1.3 GOE-level Outcomes" (heading, label, table, and
caption) a guaranteed fresh page of its own via the same pageBreak() helper
used elsewhere, rather than letting it compete for whatever space happens to
be left after the variable-length sections above it. This is the same
"give a self-contained visual block its own page" pattern each unit's
sections already use reliably. With a full fresh page always available, the
keepNext binding on the image essentially never needs to trigger a
relocation - the table and caption together (~4.3 inches) fit comfortably
within a full page's ~9 inches regardless of how long the text above them
was.

Verified with the real cumulative-outcome table at its real size, using
both a short and a deliberately long USP paragraph (the actual 80-word text
from the reported file): "1.3 GOE-level Outcomes" and the table now always
land together on their own page, "2. Unit-Wise Summary" always follows on
the very next page with a normal header gap, and a full-document sweep
found no other blank-page or orphaning anomalies.
